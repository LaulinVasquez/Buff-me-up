## Implemented behavior

Meals has an “Estimate a meal from a photo” shortcut. The existing meal-entry selector also offers it in guided and ordinary editors, including recipe adaptations. Take photo requests the phone's rear-camera chooser (`capture="environment"`); Choose photo opens the library. Browser camera/HEIC behavior depends on the device; unsupported inputs give a manual-entry fallback.

A selected image is prepared locally as a smaller JPEG preview. Nothing is analyzed until the user selects a per-photo sharing checkbox naming OpenAI and clicks Analyze. Only the normalized image and optional 300-character food/portion context are sent; profile measurements, identity, diary, targets and preferences are not part of this request. The existing meal remains unchanged until “Use estimate in meal draft.”

The result includes possible foods, a broad calorie range, nullable approximate macros and concrete uncertainties. Pictured portions can be halved or multiplied; the calorie point estimate can be corrected or left unknown. Applying it creates a one-serving label-style meal, clears ingredients/diet/allergen/group claims and ingredient review, and preserves source/range metadata. Save and log are still explicit, separate actions. Ingredient/diet suitability must be reviewed by the user before planning. Photo-based days are excluded from automatic target fitting; the source/range appears in review, saved meals, diary and plan snapshots. Switching to manual/recipe input clears the photo-derived nutrition so its source cannot silently disappear while retaining guessed numbers.

Text context/results, portion, calorie correction, editor method and step use existing per-owner, per-tab 24-hour drafts. Photos and sharing consent do not persist. Reloading does not analyze or retry; a new analysis requires choosing the image again. Cancel/success/discard remove the corresponding drafts. Completed text estimates can still be accepted after reload without re-uploading the image.

## Data and request boundaries

- Local raw file maximum: 20 MB; supported decoded JPEG/PNG/WebP and browser-decodable HEIC/HEIF. SVG/video are rejected. Client output is JPEG, inside 1280px, at most 1 MB.
- Authenticated Node route accepts only bounded JSON (1.4 MB), explicit consent version, optional bounded context and canonical inline base64 JPEG. Same-origin checks reject a supplied foreign Origin. No remote photo URL fetch, arbitrary file path or provider Files upload.
- Sharp validates bytes/pixels (at most 4,194,304 incoming pixels and 4096px per dimension), rotates orientation and re-encodes without EXIF/GPS/ICC metadata before provider use. Invalid images do not consume the paid-attempt quota.
- Five accepted provider attempts per owner per UTC day, separate from existing food (120/hour) and text-AI (10/day) counters; concurrency is atomic. An interrupted/failed provider attempt can still count. No automatic retries or analysis cache.
- Provider timeout 25 seconds, output 1,800 tokens, response body 60 KB and extracted output 18 KB. Refusal, incomplete, malformed, invalid range, excessive output and unavailable model/key fail safely without echoing provider/image details.
- `store:false`, private/no-store HTTP headers and no app image persistence, image logs or storage bucket. This does **not** promise zero provider retention: OpenAI's security/abuse controls still apply. The sharing copy links the provider's data-controls documentation.
- Ranges are rough estimates, not statistical confidence intervals or guaranteed accuracy. Hidden oils, sauces, portion depth and food recognition can change calories. Photos cannot verify allergen absence, medical-diet suitability or nutrition-label precision. Existing generic recipe estimates and exact-barcode product images remain separate features.
